REPORT 03r2 — Status DONE

## Changes
- `src/arci/descriptor.py`
  1. Unencodable integers: `_int_value` (used by both the pre-construction walk and the
     constructors) refuses an integer `json.dumps`/`hash_record` cannot write: a decimal literal
     over `sys.get_int_max_str_digits()` digits, or a `0x`/`0o`/`0b` literal whose decimal form
     exceeds it. Reported at its source path: `descriptor arci.yaml:task.x: integer too large to
     seal: more than 4300 decimal digits` (library and CLI, exit 3). Defence in depth: `_validate`
     wraps `json.dumps` (ValueError/TypeError/RecursionError -> `DescriptorError("not a JSON
     value: ...")`), `loads_descriptor` turns any ValueError/TypeError/RecursionError out of
     `parse_yaml` into `DescriptorError("invalid YAML: ...")`, and `to_manifest` also catches
     RecursionError. No bare ValueError escapes between parsing and `Manifest.create`.
  2. Shorthand rules now return a list of problems. `_condition_rule` checks the id group
     (conflict / missing / null) and the fault group (`fault`+`faults` / null `fault`)
     independently (the early return is gone); fault-level `occurrence`/`at_occurrence` was
     already collected separately. The after-validators raise the first by sorted path.
  3. Depth through shared aliases: `_check_node` returns each node's subtree height, cached by
     node id (dict replaces the `done` set). Every reuse of an already-walked node checks
     `len(path) + height > MAX_DEPTH` and raises at the use path. First visits behave as before.
- `docs/DESCRIPTOR.md` (203 lines): too-large integers and alias-aware depth in the JSON-only
  rule list; the errors section says every independent problem counts (example:
  `conditions[0].fault` sorts before `conditions[0].id`).
- `docs/schema/arci.schema.json`: unchanged (`arci schema` output identical).
- `tests/unit/descriptor/test_round2.py` (new, 18 tests): huge hex / tagged hex / decimal over
  the limit / `base_seed` / nested path, all through `compile_descriptor_text` and
  `loads_descriptor`; the largest encodable integer still seals; CLI exit 3 with
  `error: CliError: descriptor arci.yaml:task.x: integer too large ...` and no run dir; a
  monkeypatched `json.dumps` failure is a DescriptorError. Condition with id+condition_id and
  fault+faults, with and without unknown key `g`, with and without the fault-level conflict ->
  `conditions[0].fault`; `shorthand_problems` lists all three paths; null id + null fault both
  collected. Anchor chain a0..a101 under task rejected (library and `parse_yaml`); a shared
  alias reused deeper than its first use is rejected at `task.b[0][0]`; chains of 20 and
  MAX_DEPTH-2 links accepted and sealed; MAX_DEPTH-1 rejected (exact boundary).

## Deviations
- A negative hex literal (`-0x1...`) is not an integer under the descriptor's resolver (it stays a
  string, as before), so it is not among the too-large cases.
- Tests depending on the integer digit limit are skipped if the interpreter runs with the limit
  disabled (`PYTHONINTMAXSTRDIGITS=0`); then such integers are encodable and accepted.

## Open issues
- Merge-key sequences (`<<: [*a, *b]`) are counted one level deeper than the merged keys really
  sit (unchanged from 03r1; conservative, only matters at exactly depth 100).
- Not addressed (out of scope, untested): width expansion through shared aliases ("billion
  laughs"). Depth is bounded, but `json.dumps` expands each alias use, so many levels of
  many-fold aliases could exhaust memory/time on a hostile local file.
