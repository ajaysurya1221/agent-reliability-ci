# 0018: v2.4.1, fixes since 2.4.0

Record by the orchestrator, 2026-11-18. The maintainer asked for this release on 2026-11-18,
after pull requests 34, 35, 36 and 37 were merged to `main`. An independent consultant (Codex)
was asked, read-only, before the release was cut, and agreed with a patch release from what is
on `main`, with the open limits stated. Seven read-only audits and a completeness check of
`main` found no blocker.

## Why

`main` holds fixes and documents since the tag `v2.4.0`, and no new command, option, exit code,
schema, record field or fixed text. Two of the fixes were seen as failures in hosted CI: a 0-byte
`state.json` in 1 trial of 100, and the kept-table read in the six-writer test. Users of 2.4.0
have both defects. [COMPATIBILITY.md](../COMPATIBILITY.md) gives no explicit rule for a patch
release against a minor one. This record relies on the rule it states for 1.x, "a valid
existing documented command and supported record must retain its meaning" (lines 8 and 9),
which its 2.3.0 section repeats for that release ("Existing commands and records retain their
meaning."), and on the list below of what can differ.

## What ships

- **Whole-file `state.json`** (`src/arci/mcp_toolset_server.py`, `_write_whole`): the server
  for Python toolsets writes `state.json.tmp` and moves it into place. When a snapshot cannot
  be written, the previous complete state stays.
- **A staged stop of the MCP tool server** (`src/arci/mcp_boundary.py`, `_stop_server`,
  `_server_is_idle`, `stop_server`; the parent's side in `src/arci/runner.py`). An idle server
  is closed and killed at once, as in 2.4.0. Any other server has its input closed, gets
  SIGTERM at half of the time left before the trial's deadline and SIGKILL at three quarters.
  The boundary's deadline is never later than the parent's. No new outcome, termination, event
  or latch exists.
- **A bounded re-read of the kept table** (`src/arci/logs/kept.py`, `read`): the path is read
  again when it was absent at one call and present at the next, four attempts at most, no wait.
- Not code: the plugin's skill as an instruction, plugin manifest version 2.4.1; the plugin's
  README, icon and privacy page (`docs/PRIVACY.md`); one theme for the README figures; run 3 of
  the order-desk study and a post about it; the Codex reader checked against Codex CLI 0.169.0;
  updated GitHub Actions pins in the workflows and `action.yml`.

## What can differ from 2.4.0

For a command agent with an MCP tool server, in the cases where the boundary now waits,
`final_state`, and so `record_sha256`, can differ for the same spec. A server that ignores EOF
makes a trial last longer. In a narrow case named in the changelog, a trial can end in timeout
instead of completed. A tool call fully written to the server when the agent left may complete
during the wait: its effect can reach the final state, its reply is discarded unrecorded.
Stored records are not re-graded.

## Known gaps against pinned text, not closed by this release

1. `docs/AGENT_SEMANTICS.md`, line 211: "Determinism: for a scripted client the envelope must be
   identical across runs." The staged stop narrows the timing dependence of the graded final
   state and does not remove it. The cases are listed in the changelog.
2. Record 0017, lines 561 to 563: "With `--keep`, a table that could not be read is not
   replaced and not changed; the run goes on, F24 says so, and the exit code is the one of the
   result." When only the read under the directory lock finds the table unreadable, the run
   drops the write without F24.

Neither pinned text is weakened or reinterpreted by this record; both gaps stay open as defects
to fix. Also, `docs/AGENT_SEMANTICS.md` (lines 165 and 166) lists the boundary's config as
"(spec, nonce, socket path, workdir)". The parent now also passes the seconds left and its
deadline in it: the list is incomplete; the config is internal and outside every sealed record.

- `src/arci/__init__.py`: `__version__ = "2.4.1"` (not a frozen file; listed for completeness).

## Order of publication

The skills and the plugin on `main` name `realornoise==2.4.1` from the merge until both publish
jobs finish, so a run of the skill in that window fails at install. The tag is pushed on the
merge commit only after hosted CI on it is green. The main package is published before
`realornoise`. The publish action's updated pin runs for the first time at this tag; RELEASING.md
says what to do when a publish job fails. A plugin directory that reviewed manifest version
2.4.0 may keep that copy; no claim is made about when a directory or an installed copy updates.

## What the release may and must not say

Fixes, a changed plugin skill, updated Action pins and documents; no new feature. It may not
say that the final state is now deterministic, that `--keep` never loses a day, or that an
installed plugin updates by itself. Otherwise as in 0013 and 0014.
